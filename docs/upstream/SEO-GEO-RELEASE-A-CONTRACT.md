## 1. Product objective

Rubik SEO/GEO Core must make every site generated by the platform **search-ready by default**, with the highest possible degree of safe automation from real client data.

Canonical flow:

```text
BUSINESS DATA
→ PROJECT STATE
→ SEO/GEO DECISION ENGINE
→ METADATA + SCHEMA + CONTENT + MEDIA + BLOG + LOCAL SEO
→ PUBLISH
→ AUDIT + REAL MEASUREMENT
```

Release A covers the first production-ready slice:

```text
BUSINESS DATA
→ PROJECT STATE
→ SENIOR SEO DECISION ENGINE
→ HOME SEO
→ PRODUCTIVE PUBLISHER
→ PRE-PUBLISH AUDIT
```

No second Store, CMS, database, Media Library or parallel application may be introduced.

## 3. Spain-first contract

Release A supports **Spanish SEO only**.

Canonical runtime configuration:

```text
language = es
locale = es-ES
supportedLanguages = [es]
```

The current English selector / pseudo-bilingual formulas must be removed or disabled from the operational Studio UI.

### Technical debt

Register explicitly:

```text
TECH DEBT · MULTILINGUAL SEO
```

Future multilingual support must mean real localized content, not string substitution. It requires:

- content by locale;
- metadata by locale;
- Page Registry by locale;
- canonical by locale;
- hreflang only for real equivalent URLs;
- schema/inLanguage by locale;
- AUTO/CUSTOM state by locale;
- human-reviewed translation/localization workflow.

Do not simulate English by translating only `Restaurante → Restaurant` or `en → in`.

## 4. SEO quality standard

The system is not a static template filler. It acts as a deterministic **Senior SEO Decision Engine**.

Required characteristics:

- deterministic;
- versioned;
- explainable;
- testable;
- data-driven;
- no invented facts;
- no keyword stuffing;
- no fake ranking / AI visibility claims.

Decision flow:

```text
SOURCE DATA
→ generate valid candidates
→ apply hard rules
→ evaluate quality
→ select best candidate
→ store provenance
```

Every AUTO generated field must preserve at least:

```js
{
  mode: 'auto',
  value: '',
  templateId: '',
  derivedFrom: [],
  decisionReason: '',
  updatedAt: ''
}
```

CUSTOM always overrides AUTO. Returning to AUTO recalculates from current Source Data.

## 6. HOME title decision model

The approved formula is a candidate, not a mandatory literal string.

Candidate family may include:

```text
{{brand}} | {{category}} en {{city}}
{{category}} en {{city}} | {{brand}}
{{brand}} | {{primaryCuisineOrService}} en {{city}}
{{brand}} | {{category}}
```

The engine selects the best valid candidate using, in order:

1. actual HOME intent;
2. specificity;
3. real local signal when city exists;
4. real category/cuisine/service data;
5. natural Spanish;
6. absence of redundancy;
7. consistency with visible content/H1;
8. branding.

Length is advisory only, never a rigid Google limit.

Fallbacks must degrade gracefully when data is incomplete.

## 7. HOME meta description — canonical composition strategy

The old simplified implementation (`brand + category + hero.body`) is insufficient.

The canonical composition strategy is:

```text
BRAND
+ WHAT IT IS
+ SPECIALITY / PRIMARY SERVICE
+ LOCATION
+ REAL VALUE PROPOSITION
+ REAL CTA
```

Each component is conditional and must only appear when supported by Source Data.

Full example:

```text
LÚMINA es un restaurante gastronómico de cocina mediterránea contemporánea en Alicante. Descubre una carta de producto y temporada y reserva tu mesa.
```

Rules:

- `reserva tu mesa` only if a real reservation capability/URL exists;
- cuisine only if known;
- locality only if known;
- offer/value proposition only if present in real source content;
- no synthetic claims;
- natural Spanish, not mechanical concatenation;
- if data is incomplete, generate a truthful reduced version and raise an audit opportunity/warning.

## 8. H1 contract

The engine may recommend the best H1, but must not create hidden duplicate H1s or silently overwrite approved editorial copy.

Rules:

- detect the existing visible H1;
- keep exactly one principal visible H1 as the product editorial rule;
- align recommendation and public H1 explicitly;
- never inject a second hidden H1 for SEO;
- if human copy remains CUSTOM, preserve it and audit consistency instead of silently replacing it.

## 9. Senior pre-publish audit

A string existing is not equivalent to SEO quality.

Every relevant field is evaluated across:

```text
EXISTENCE
COMPLETENESS
SPECIFICITY
CONSISTENCY
PUBLISHABILITY
```

Canonical severities:

- `BLOCKER` — prevents safe/valid production SEO or may break indexation;
- `ERROR` — serious issue in active Release scope;
- `WARNING` — important quality issue;
- `OPPORTUNITY` — non-mandatory improvement;
- `PASS` — valid and sufficiently complete for the evaluated contract;
- `DEFERRED` — intentionally belongs to a later Release and must not reduce Release A readiness.

Examples:

- generic fallback category only → WARNING or OPPORTUNITY;
- local business without city → WARNING;
- no cuisine/service differentiator → OPPORTUNITY;
- generic title despite richer source data → WARNING;
- title/H1 contradiction → WARNING;
- invented factual data → ERROR/BLOCKER;
- missing productive canonical at publish time → BLOCKER;
- OpenSEO/Search Console/DataForSEO not yet implemented → DEFERRED, not BLOCKER.

No fake score such as `Google Rank Score` or probability of ChatGPT citation.

## 10. Release A Publisher contract

Release A must publish the SEO, not merely preview it.

Required productive outputs:

```html
<title>...</title>
<meta name="description" content="...">
<link rel="canonical" href="...">
<meta name="robots" content="...">
<meta property="og:type" content="...">
<meta property="og:title" content="...">
<meta property="og:description" content="...">
<meta property="og:url" content="...">
<meta property="og:image" content="...">
<meta name="twitter:card" content="summary_large_image">
```

Plus productive JSON-LD and generated sitemap/robots policy.

### Critical technical requirement

Productive metadata must exist in the **initial served/published HTML output**. It must not depend exclusively on client-side JavaScript mutating `document.head` after load.

Acceptance must include raw HTML validation via HTTP/fetch/curl or equivalent with JavaScript disabled/not executed.

## 11. Productive schema contract

For Restaurant HOME, emit a coherent graph where real data exists:

```text
WebSite
→ WebPage
→ Restaurant
```

Optional nodes/properties only from real public data:

- PostalAddress;
- GeoCoordinates;
- OpeningHoursSpecification;
- image;
- servesCuisine;
- telephone;
- email;
- priceRange;
- menu;
- reservation capability/URL;
- sameAs;
- Person/chef only when real and relevant.

Never generate fake `aggregateRating`, reviews, people, hours or coordinates.

Structured data must agree with visible/public content.

## 12. Canonical, robots and environment policy

Rules:

- Vercel preview URL is never canonical;
- productive canonical derives from valid `seo.site.baseUrl` + Page Registry;
- missing valid productive base URL at publish time = BLOCKER;
- preview/staging = noindex/protected policy;
- production = index/noindex according to Page Registry;
- preview noindex must never leak accidentally into production;
- production index policy must never make preview indexable.
